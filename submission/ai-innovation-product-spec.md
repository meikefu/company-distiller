## 三、核心要素

### 1. 真问题：真实痛点与用户角色

#### 1.1 真实业务场景

在客户拜访、账户复盘或商机推进前，大客户经理需要回答几类直接影响行动的问题：

- 客户是谁，法律实体、业务单元、产品和账户边界分别是什么；
- CRM 中的商机目前处于什么阶段，该信息是什么时间观察到的；
- 访谈里谁在什么时间说过什么，后续是否有更正或撤回；
- 合同证明了哪些义务，哪些内容并不能证明产品已经被实际采用；
- 产品使用量、服务工单和风险信号是否支持当前判断；
- 哪些信息能给销售看，哪些只能给客户成功、管理层或公众看。

这些信息通常分散在公开资料、CRM、访谈、合同、工单和产品使用数据中。传统做法往往是临时搜索、复制到文档、人工拼接成一份静态摘要。摘要一旦生成，来源、有效时间、冲突、撤回和权限边界很容易丢失；下一次更新时又要重复整理。

当前仓库能证明这套问题模型已经被实现，但还缺少实际客户经理的访谈记录、现行流程截图和匿名任务计时。正式申报时至少应补充 1 位真实目标用户、1 个匿名账户和 1 次同输入对照，并如实标注这是 `n=1` 的探索性试测；更可靠的验证建议覆盖不少于 10 个账户。

#### 1.2 一线真实痛点

| 痛点 | 对一线工作的影响 | 常见认知错误 |
|---|---|---|
| 数据分散 | 拜访准备需要在多个系统和文档间来回切换 | 漏掉最新工单、访谈修正或合同版本 |
| 信息口径不同 | 同一客户在 CRM、合同、用量系统中的对象边界不同 | 把卖方账户状态写成客户公司属性 |
| 静态报告易过期 | 新信息只能覆盖旧文档，历史依据难保留 | 无法回答“当时知道什么、后来为何改变” |
| 事实和推断混写 | AI 摘要语气流畅，但认识论边界不清 | 把 CRM 阶段当采购意向，把使用量当满意度 |
| 来源不可追溯 | 客户经理无法快速复核结论 | 关键判断无法定位到原始证据和日期 |
| 受众边界模糊 | 同一份材料被复制给不同角色 | 合同、工单或使用信息误进入公开视图 |

#### 1.3 为什么适合用 AI

这不是单靠字段搬运就能解决的问题。访谈、公开材料、合同条款和工单描述包含大量非结构化语义，必须理解主体、时间、口径、证据强弱以及“事实、转述、观察、推断、假设、义务”的差别。AI 适合承担：

- 非结构化文本理解和实体候选识别；
- 从不同来源抽取原子 Claim 和关系候选；
- 判断新信息是强化、替代、冲突、撤回还是暂不发布；
- 根据证据生成面向具体任务的可读公司视图。

但 AI 不应独自决定数据契约、权限边界和历史写入。Company Distiller 采用“**AI 负责语义候选，确定性程序负责校验与交付**”的组合：Prompt 负责理解，Schema、摘要、追加式账本、快照、策略过滤和验收门禁负责约束。这是项目区别于普通企业摘要 Prompt 的关键。

#### 1.4 目标用户角色

**核心使用者：大客户经理。**

核心任务是在有限时间内形成一份可用于拜访或账户复盘的客户认知，并能回答每项结论的来源、日期、状态和可见范围。客户经理保留最终业务判断权，产品不自动代替其作出采购意愿、赢单概率、满意度或合规结论。

扩展角色包括售前、客户成功、知识运营和管理层，但不是本次申报的主叙事。

### 2. 真工具：AI 做法与搭建过程

#### 2.1 技能名称

**Company Distiller（公司蒸馏器）**

#### 2.2 绑定的原子能力

> 将指定企业的公开资料、CRM、访谈、合同、工单和产品使用数据持续蒸馏为带证据、时间、冲突、审核状态和生命周期的公司对象，再按受众和用途导出受控 Company Skill。

该原子能力由六个连续环节组成：

1. 盘点公司边界、数据源版本、受众和用途；
2. 路由并保留六类来源的结构化语义；
3. 由 AI 生成实体、Evidence、Claim 和 Relation 候选；
4. 对比当前快照，判断新增、强化、替代、冲突、撤回或不变；
5. 通过确定性校验后追加到版本化公司对象；
6. 从同一快照导出 `public`、`sales`、`customer-success` 和 `executive` 受控视图。

#### 2.3 触发方式

在 Codex 中调用：

```text
使用 $company-distiller，为目标企业构建或增量更新公司对象。
输入包括公开资料、CRM、访谈、合同、工单和产品使用数据；
本次输出 sales / account-planning 视图，所有结论保留证据和日期。
```

#### 2.5 核心系统指令 / Prompt 结构

```text
角色设定（Role）:
你是一名企业证据蒸馏专家。你的工作不是写一篇看似完整的公司介绍，
而是把多源数据转化为可追溯、可更新、受治理的公司知识候选。

任务目标（Objective）:
针对指定企业，从公开资料、CRM、访谈、合同、工单和产品使用数据中，
生成符合 Schema 的 Entity、Record/Event、Evidence、Claim 和 Relation 候选；
再基于当前 Snapshot 判断知识如何演化，并按目标受众生成受控视图。

工作步骤（Workflow）:
1. 确认公司、法律实体、业务单元、账户、产品和人员/角色边界。
2. 固定每个数据源的版本、哈希、业务日期、观察时间和策略。
3. 保留结构化 Record/Event，不得先压缩成散文摘要。
4. 抽取原子 Claim；区分 fact、statement、observation、inference、
   hypothesis、risk 和 obligation。
5. 为每条 Claim 绑定 Evidence、有效时间、观察时间、置信度和策略。
6. 与当前 Snapshot 比较，标注 new、reinforced、superseded、
   conflicted、retracted 或 unchanged。
7. 未经直接证据支持，不得把 CRM 阶段解释为采购意愿，
   不得把合同解释为采用，不得把工单扩大为公司级缺陷，
   不得把使用量解释为满意度。
8. 输出结构化候选，由确定性校验器完成最终写入和投影。

输出要求（Output Contract）:
- 只输出符合仓库 JSON Schema 的候选对象；
- 每项结论必须有稳定 ID、主体、时间、证据和策略；
- 冲突必须保留，不得静默合并；
- 假设在审核前保持 proposed，不得进入当前视图；
- 不直接修改历史 Claim 或生成物。
```

#### 2.6 搭建过程

1. **先建本体边界**：把“公司”“商业关系”“产品使用与服务”分成三个相连但不混淆的域。
2. **定义最小知识单元**：以带主体、谓词、值、类型、双时间、证据和审核状态的 Claim 取代大段摘要。
3. **设计多轮蒸馏协议**：每轮输入形成不可变 run bundle，校验后追加账本并生成新 snapshot。
4. **建立知识生命周期**：支持新增、强化、替代、冲突、撤回和不发布，历史不被覆盖。
5. **建立受众投影**：同一规范快照按受众和用途白名单导出，不把原始记录载荷复制到交付 Skill。
6. **把质量规则代码化**：建设 15 个 Schema、16 项发布门禁以及单元/集成测试。
7. **建设三轮合成案例**：依次加入公开资料、CRM/访谈、合同/工单/使用数据，验证持续更新和视图隔离。

#### 2.7 核心技术与竞争力

| 能力 | 普通静态企业摘要 | Company Distiller |
|---|---|---|
| 知识形态 | 一篇被覆盖的文本 | 版本化的 Claim、证据、关系和快照 |
| AI 输出 | 自由文本 | 受 Schema、证据、时间和审核状态约束的候选 |
| 更新方式 | 重写整份报告 | 追加 run，记录强化、替代、冲突和撤回 |
| 事实边界 | 容易把观察或推断写成事实 | 显式区分九类 Claim 认知类型 |
| 时间语义 | 通常只有“最新” | 同时保存业务有效时间和系统观察时间 |
| 可追溯性 | 来源链接常停留在文末 | Claim 可闭合追溯到 Evidence、Record/Event、Source 和 Run |
| 多角色交付 | 同一份文档复制分发 | 同一快照生成四类受众白名单投影 |
| 可复验性 | 依赖人工抽查 | 摘要校验、确定性重放、16 项自动门禁 |

真正的差异不在“让 AI 写得更快”，而在于为 AI 生成的企业认知增加证据、时间、生命周期和受众边界，使结果能够持续更新、复核和重新交付。当前尚无竞品对照或市场采用数据，因此不宣称已经形成商业壁垒或行业领先。

#### 3.5 业务试测补录表（正式提交前必须完成）

| 平均查询系统/资料数量 | 待实测 | 待实测 | 每个账户实际打开的数据源数量 |
| 人工流转节点 | 待实测 | 待实测 | 不同人员/系统间的手工交接次数 |

| Claim 证据可追溯率 | 待实测 | 待实测 | 可定位到有效证据的 Claim 数 / 抽检 Claim 总数 |
| 增量刷新中位耗时 | 待实测 | 待实测 | 输入新数据到更新视图完成 |
| 识别并保留的冲突数 | 待实测 | 待实测 | 人工确认的真实冲突数量 |
| 敏感信息误投影数 | 待实测 | 待实测 | 不应出现但出现在目标视图的条目数 |

节省工时的计算公式：

```text
月节省工时 = （传统流程中位耗时 - Skill 流程中位耗时）
             × 月均处理账户数 ÷ 60
```

不要由节省时间直接推导赢单率。只有在有足够样本、明确对照和观察周期后，才单独报告商机推进或赢单变化。

#### 3.6 可复制价值与转化潜力

可复制场景包括客户拜访准备、账户计划、续约复盘、客户健康度解释、重点客户交接和管理层账户审查。其他团队复用需要满足：

1. 明确目标企业、法律实体、账户和产品边界；
2. 对上游 CRM、合同、工单等字段做一次语义映射；
3. 确认每类数据的所有者、受众、用途和保留规则；
4. 在进入运行包前完成个人标识令牌化和敏感原文治理；
5. 建立 AI 候选审核和人工最终复核责任；
6. 生产化时补充连接器、编排、事务数据库、认证授权、加密和审计。

从产品化角度看，当前仓库可作为企业客户知识产品的语义内核和验收基线，而不是开箱即用的生产 SaaS。

## 六、能力边界与风险声明

- 当前是本地参考实现，不提供在线 CRM、合同、工单或数据仓库连接器；
- 当前没有在脚本中直接调用独立模型 API，AI 语义生成由 Codex 宿主执行；
- 没有 Web UI、作业编排、数据库事务、跨进程锁、租户隔离、认证、加密和自动保留执行；
- `16/16` 门禁证明结构、治理和确定性，不证明抽取准确率或业务收益；
- 本地策略是语义过滤规则，不是操作系统文件访问控制；
- 生成结果不构成法律、投资、采购、安全或合规意见；
- 示例数据完全合成，不可作为真实客户效果数据。

主动说明边界不是削弱产品，而是证明项目遵守“三真原则”：已经完成的能力给出可复验证据，尚未完成的能力给出明确的产品化路线。
