# 数据路由

每项输入都必须依次经过来源版本、结构化记录或事件、可定位证据，再形成断言或关系候选。全过程保留源系统语义。

## 来源路由

| 来源 | 规范记录或事件 | 主要领域 | 常见断言 |
|---|---|---|---|
| 监管申报或审计报告 | `public_fact`、`company_update` | 公司 | 身份、指标、风险、官方陈述 |
| 官网、产品页或定价页 | `public_fact`、`company_update` | 公司 | 产品、定位、定价陈述 |
| 管理层访谈或电话会议 | `interview_segment`、`interview_conducted` | 公司或商业关系 | 有归属的陈述、限定范围的推断 |
| CRM 客户或联系人 | `crm_account`、`crm_contact` | 商业关系 | 销售方观察到的生命周期与角色 |
| CRM 商机或活动 | `crm_opportunity`、`crm_activity`、阶段事件 | 商业关系 | 已观察阶段、异议、输赢信号 |
| 客户访谈 | `interview_segment`、访谈事件 | 商业关系 | 有归属的痛点、优先级、异议、结果 |

## 来源权重

来源权重取决于它支撑的具体断言，而不只取决于文件类型。已签合同对签约方和义务具有高可靠性，却不能证明使用情况或满意度；CRM 行对“系统记录了什么”具有高可靠性，却不能证明客户真实意图；工单对已记录个案具有高可靠性，却不能代表全部部署的事故率。

置信度包含以下维度：

- 来源可靠性 `source_reliability`：`low`、`medium`、`high`；
- 交叉印证 `corroboration`：`none`、`single`、`multiple`；
- 推断强度 `inference_strength`：`direct`、`derived`、`speculative`；
- 综合等级 `overall`：`low`、`medium`、`high`。

## 必经处理流程

1. 创建来源版本，记录连接器、外部 ID 与版本、哈希、定位信息、来源或业务日期、观察时间及治理策略。
2. 在提取断言前解析稳定实体。
3. 把来源行规范化为所需 `record_type`，不得丢弃 `references/system-architecture.md` 列出的必要字段。
4. 为变更和实际发生的事项创建事件。
5. 创建最小证据单元，并通过精确定位信息链接到来源、记录或事件。
6. 创建原子断言和关系，同时执行策略继承。
7. 与当前快照比较，并使用生命周期链接表达变化。

## 冲突处理规则

1. 只有主体、谓词含义、范围、期间、单位和会计或计量口径均匹配的陈述才能直接比较。
2. 不同期间或口径的陈述应保留为不同断言。
3. 未解决的互斥观点都应保留，并通过双向或可发现的 `contradicts` 链接关联。
4. 用 `supersedes` 纠正早期断言；撤回时新增一条撤回断言。
5. 支撑断言发生变化时，必须重新评估下游推断。

## 隐私与用途

数据分类以及受众和用途权限必须向下继承。直接个人标识符应尽可能令牌化。原始访谈、合同、工单、CRM 和遥测数据的定位信息只保存在规范工作区。生成的 Skill 仅复制获授权的溯源摘要，不包含原始记录或事件载荷。
