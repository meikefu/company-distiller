# 优化计划

本计划把 Company Distiller 从一次性 Markdown 生成器升级为版本化的公司对象蒸馏系统。生成的 Skill 是受治理的公司对象投影，不是事实来源。

## 目标结果

系统必须支持在多轮运行中摄取公开与内部公司数据，保留各来源的结构语义，维护不可变溯源，生成确定性快照与差异，并在不泄露无权访问证据的前提下导出面向不同受众的 Skill。

## 工作计划

| 阶段 | 交付物 | 完成证据 |
|---|---|---|
| 1. 契约 | 实体、来源、记录、事件、证据、断言、关系、策略、运行和快照的机器可读 schema | 所有规范 JSON/JSONL 行均通过验证，非法样例验证失败 |
| 2. 增量核心 | 可初始化的公司对象工作区和仅追加运行机制 | 三个连续运行包成功应用，过期基准快照和重复 ID 的运行失败 |
| 3. 变更语义 | 快照物化和每轮运行的变更日志 | `new`、`reinforced`、`superseded`、`conflicted`、`retracted` 和 `unchanged` 均有测试 |
| 4. 治理 | 策略继承和受众投影 | `public`、`sales`、`customer-success` 和 `executive` 导出只含获授权的断言和证据 |
| 5. 运行时包 | 包含公司概览、事实、时间线、断言、证据、安全溯源、关系和过期处理协议的公司 Skill | 每个导出 Skill 都通过严格验证，且不含原始记录或事件载荷 |
| 6. 评估 | 结构、溯源、时间、重放、隐私和行为验收门 | `python3 scripts/run_acceptance.py` 以状态码 `0` 退出 |

## 架构决策

1. 保持原始系统的权威性。存储来源定位信息、哈希、规范化记录和证据，不把 Markdown 当作数据库。
2. 将公司身份、商业关系和产品使用建模为相互关联但彼此独立的领域。
3. 一轮运行是基于单一快照的不可变变更批次。不得修改早期断言来伪造当前历史；当前本地实现不承诺数据库事务。
4. 用 `supersedes` 表示纠正，用 `contradicts` 表示矛盾，用撤回断言表示退出。
5. 同时跟踪现实世界中的业务有效期和系统观察时间。
6. 在物化 Skill 前应用访问策略。提示词不能充当访问控制边界。
7. 保留 CRM、合同、工单和使用数据的结构化记录。可以把它们蒸馏为可发布断言，但不能抹平来源账本。

## 延后范围

Salesforce、HubSpot、Zendesk、数据仓库和合同系统的在线连接器暂不实现，但连接器输出契约不能延后：离线运行包使用相同的实体、记录、事件和溯源 schema，未来连接器必须生成同样的结构。

图数据库和向量数据库只是存储优化，不是前置条件。JSON/JSONL 参考实现优先保证可移植、可测试。

## 完成定义

只有 `references/evaluation-rubric.md` 中全部验收门通过，优化才算完成。仅有文档、示例输出、绿色语法检查或自编场景答案均不充分。
